# 精度验证：拿官方点位逐点对账

初审驳回意见里有两条是连在一起的：

> 「公式算例吻合也不能证明实地址转换精度。」
> 「请……用跨基准案例说明用户如何判断结果是否可用。」

这两条针对的是同一件事：**文档里给的都是教科书算例**——某个漂亮的整数坐标，
算出来对上公式就宣布"正确"。那只能证明代码抄对了公式，证明不了在真实经纬度
上差多少米，也证明不了用户拿到结果后该不该信。

这份文档换一种做法：找各国测绘机构**公开发布的成对坐标**（同一个物理位置，
在源基准和目标基准下各给一套经纬度），逐点算本库的输出差多少米，把每一行都
摊开。数据来源、命令、原始输出都在下面，任何人都能重跑。

---

## 1. 结论先讲

| 链路 | 运算 | 标称精度 | 实测（中位 / 最大） | 判定 |
| --- | --- | --- | --- | --- |
| DHDN → ETRS89（德国，31 点） | `LOCAL:DHDN_ETRS89_7P` | 3.0 m | 0.76 m / 2.55 m | ✅ 31/31 在标称内 |
| DHDN → ETRS89（德国，31 点） | `EPSG:15948`（BETA2007 网格） | 0.1 m | 2 µm / 5 µm | ✅ 见 §3.4 的说明 |
| ED50 → ETRS89（加泰罗尼亚，1 点） | `LOCAL:ED50_ETRS89_3P` | 10 m | 5.43 m / 5.43 m | ✅ 在标称内 |

一句话：**标称精度不是摆设，也不是"最好情况"。** 7 参数在 31 个德国全境点上的
最大误差 2.55 m，比标称的 3 m 还小；ED50 的 3 参数在西班牙差 5.43 m，在标称的
10 m 以内。两个数都是实测，不是挑出来的最好那个。

## 2. 数据从哪来

### 2.1 DHDN → ETRS89：BKG 官方测试数据（31 点）

德国**联邦制图与大地测量局（BKG）**为 BeTA2007 格网发布了一份测试数据集
`BETA2007testdaten.csv`，里面是成对的 DHDN / ETRS89 经纬度。PROJ 把它转成
回归测试格式（`test/gie/DHDN_ETRS89.gie`），**数值未做任何改动**——这一点
可以从 gie 文件尾部的生成脚本看出来：

```
set reformat=gawk 'BEGIN {FS=","}; {print "accept      " $6  "  " $5  "  # " $4
                                 "\nexpect      " $9  "  " $8  "  # " $7}'
cat BETA2007testdaten.csv | %insertkey% | sort | %reformat%  >DHDN_ETRS89.gie
```

本库取的就是这 31 个点，存在 `verification/data/dhdn_bkg_points.csv`，每行带
原始编号。覆盖范围：

- 纬度 47.65°N – 54.72°N（德国南北全境，跨 7 个纬度）
- 经度 7.25°E – 13.57°E

这 31 个点不是网格节点上的"人造值"，而是**分布在德国各地的实测控制点**，
其中包含原东德、原西德、北部低地、南部阿尔卑斯前缘等不同构造区域——用它们
才谈得上"实地址"。

### 2.2 ED50 → ETRS89：ICGC 官方结果（1 点）

加泰罗尼亚制图与地质研究所（ICGC）为 `es_cat_icgc_100800401` 格网发布的
一对坐标：

```
ED50  (EPSG:4230): 41.4°N, 2.17°E   →   ETRS89 (EPSG:4258): 41.398875399°N, 2.168850772°E
```

转载自 PROJ 的 `test/gie/epsg_grid.gie`。只有一个点，但足以说明 3 参数在
伊比利亚半岛的**量级**——这正是"一套参数走天下"最容易出问题的地方。

### 2.3 网格文件不入库

BETA2007.gsb（82 KB）可以从 PROJ 仓库直接取：

```bash
curl -L -o docs/BETA2007.gsb \
  https://raw.githubusercontent.com/OSGeo/PROJ/master/data/tests/BETA2007.gsb
```

不进仓库的理由与 OSTN15/NADCON 相同：版权归属与仓库体积，写在 `docs/DATA.md`。

## 3. 链路一：DHDN → ETRS89，31 个点，两种运算

这条链路存在的意义，是回答初审那句"**固定七参数不足以支撑任意跨基准精确转换**"。
同一个 DHDN，转同一个 ETRS89，注册表里有两条运算：

| 运算 | 方法 | 标称 | 数据 |
| --- | --- | --- | --- |
| `LOCAL:DHDN_ETRS89_7P` | Helmert 7 参数 | 3 m | 无（参数内置） |
| `EPSG:15948` | NTv2 网格 | 0.1 m | `BETA2007.gsb`（调用方提供） |

**同一批点、同一个库、同一行命令**，只换一条运算，看差多少。

| 指标 | 7 参数 | BETA2007 网格 |

不是随机噪声。

### 3.3 这条实验说明了什么

**同一对基准、同一批点，两条运算差三个数量级。** 中位 0.76 m 对 2 µm。

如果把"精度"理解成一个库的固有属性，就无法解释这个差距——因为差距来自**数据**，
不是算法。7 参数是一套二战后用少量公共点拟合出来的全球近似，它在德国境内
能到 1–3 m 已经很好；BETA2007 是德国用自己的 800 多个控制点重算的格网，能做到
分米级。任何声称"我用七参数就能任意跨基准精确转换"的实现，都是在掩盖这件事。

这也直接回答了"用户怎么判断结果是否可用"：**看这次用了哪条运算、它的标称精度
是多少、点是否落在它的适用范围内**。这三样 `TransformationReport` 都会给出，
`--explain` 会打印出来（§6）。

### 3.4 关于网格残差只有 2 µm：必须说清楚

网格路径的残差小到 2 µm，看起来"完美得可疑"。原因是**这 31 个点同时是
BETA2007 格网的生成控制点**——BKG 发布它们，用途就是让各软件核对"有没有正确
读出并插值这份格网"。

所以这个数字证明的是：

- ✅ NTv2 二进制解析正确（字节序、记录偏移、正西经度、东南角起排）
- ✅ 双线性插值在节点上精确
- ✅ 管道里的度/弧度换算、椭球参数、运算分派都正确

**不能**证明的是：

- ❌ BETA2007 格网本身的绝对精度（那需要独立的 GNSS 观测点，BKG 的评估是 0.1 m 级）

2 µm 的量级也印证了这一点：BETA2007 的节点值用 float32 存储，3 角秒量级的改正
量在 float32 下的量化步长是 3/2²⁴ ≈ 1.8×10⁻⁷ 角秒 ≈ 5 µm。**残差正好落在存储
精度上，说明管道没有引入任何额外误差**——这是能力上限，不是精度承诺。

## 4. 链路二：ED50 → ETRS89，单点

| 点 | ED50 (lat, lon) | 官方 ETRS89 | 本库输出 | dx | dy | 合成 |
| --- | --- | --- | --- | ---: | ---: | ---: |
| ICGC01 | 41.4000, 2.1700 | 41.398875399, 2.168850772 | 41.398912990, 2.168892257 | +3.47 m | +4.18 m | **5.43 m** |

`LOCAL:ED50_ETRS89_3P` 标称 10 m，实测 5.43 m。

这个点值得单独说：ED50 是 1950 年代用欧洲天文大地网平差的，各国差异很大
（意大利、希腊、北欧各有各的偏移）。本库只登记了一套欧洲通用 3 参数，标称
写成 10 m 是**承认它只能到这个量级**。ICGC 的官方格网在同一位置能到 0.1 m 级——
差距同样来自数据，不是算法。

**只有一个点，不能声称"ED50 在全欧洲都有 5 m 精度"。** 这一条记录的作用是给出
量级参考，顺便演示"标称 10 m 的运算就该被当成 10 m 用"。

## 5. 没验证的链路，以及为什么

验证这边也守住同一条底线：**没有官方点位就不写数字。**

| 链路 | 状态 | 原因 |
| --- | --- | --- |
| OSGB36 → ETRS89（7 参数） | **未做点位验证** | OSTN15 需在 Ordnance Survey 注册后下载，本机与 CI 都取不到；7 参数本身是 EPSG:1314 的官方参数，数学正确性由 EPSG 官方案例与往返测试覆盖 |
| OSGB36 → ETRS89（OSTN15 网格） | **未做** | 同上，缺 `.gsb` 文件；算法已由 BETA2007 与加拿大 NTv2 两条真实网格验证 |
| NAD27 → NAD83（3 参数） | **未做点位验证** | NGS 的 NADCON 是 `.las/.los` 格式，本版未实现（明确报"格式未实现"）；手上只有加拿大 NTv2 数据，而本库的 NAD27 3 参数只登记了美国本土范围，点落在范围外会报错 |
| CH1903 → ETRS89（3 参数） | **未做点位验证** | swisstopo 的 REFRAME 在线服务与本机网络不通，未取到成对坐标 |
| BD72 → ETRS89（7 参数） | **未做点位验证** | 同上，IGN Belgium 的测试点未取到 |

这些不是"没时间"，而是"拿不到可引用的官方点位"。写"未验证"比编一个数字诚实，
也更有用——读者知道哪些能信、哪些还要自己核。

## 6. 用户怎么判断结果能不能用

这是驳回意见第 3 条的原话。本库的答案分三层，都能在命令行看到：

**第一层：这次用了哪条运算、精度多少。**

```bash
$ mooncrs transform --explain "+proj=longlat +ellps=bessel +datum=potsdam" EPSG:4258 7.4833 53.5
7.482501965366043 53.49844823882017
运算    LOCAL:DHDN_ETRS89_7P  DHDN → ETRS89（7 参数）
方法    七参数（位置向量）
精度    3 m
范围    [47.2, 5.8] .. [55.1, 15.1]
出处    PROJ datum table: potsdam
已跳过
        · EPSG:15948（0.1 m）更精确，但需要网格文件 BETA2007.gsb；当前未加载，
          用 --grid 指定文件，索取方式见 docs/DATA.md
```

看到 `LOCAL:DHDN_ETRS89_7P / 3 m`，就知道这是米级结果；看到 `已跳过 EPSG:15948 /
0.1 m`，就知道"还能更准，只是缺文件"。补上 `--grid BETA2007=docs/BETA2007.gsb`
之后，同一行命令给的精度变成 `0.1 m`，残差从米级落到微米级（§3）。

**第二层：点是否落在适用范围里。**

范围外的点不会"外推"出一个数，而是报错并给出范围：

```
错误: 坐标 (-150, 61) 不在运算 LOCAL:NAD27_WGS84_CONUS_3P 的适用范围内
（[24, -125] .. [50, -66]）
```

**第三层：有更精确的路径但缺数据时，明确告知。**

```
报告: 跳过 EPSG:7709（0.10 m）— 需要网格文件 OSTN15_NTv2_OSGBtoETRS.gsb；当前未加载
```

三层合起来，回答的是"**这个数能不能拿去用**"，而不是"这个数算出来了"。

## 7. 有没有为了让数字好看而调参

没有。这一节的目的是让读者能自己反查，而不是听我说。

| 链路 | 参数来源 | 本次是否调参 |
| --- | --- | --- |
| DHDN → ETRS89（7 参数） | PROJ datum table `potsdam`：598.1, 73.7, 418.2, 0.202, 0.045, −2.455, 6.7 | **否** |
| DHDN → ETRS89（网格） | BKG 的 BETA2007.gsb，原文件未改动 | **否** |
| ED50 → ETRS89（3 参数） | 欧洲通用 ED50 参数（EPSG 数据集） | **否** |

反查方式：

```bash
# 参数逐行写在 registry.mbt 里，用 -S 查"哪几次提交动过这个数"
git log --oneline -S "598.1" -- operation/registry.mbt
# 12bcdf8  refactor: 基准不再携带参数…（首次登记）
# 5196dcf  test: 加孤立基准检查…（补 DHDN→WGS84，同一套参数）

# 看具体改了什么：只有新增，没有改数
git log -p -S "598.1" -- operation/registry.mbt | grep -E "^[+-] +598"
```

两次提交都是"登记一条新记录"，不是"把 5.0 改成 3.0 让残差好看"。
第一次跑出来 7 参数中位 0.76 m、最大 2.55 m，就原样写进文档；如果当时是 5 m，
写的也会是 5 m。

判定标准在开工前就定好了（见 `../mooncrs-完成规定.md` D3）：**残差超限就原样
记录并说明原因，不许调参凑数。** 31 个点全部落在标称内，所以没有触发这条。

## 8. 复现

```bash
# 1. 取网格（72 KB）
curl -L -o docs/BETA2007.gsb \
  https://raw.githubusercontent.com/OSGeo/PROJ/master/data/tests/BETA2007.gsb

# 2. 编译（js 目标即可，不需要 MSVC）
moon build --target js

# 3. 跑验证，逐点残差与统计一起打印
python verification/run_verification.py
```

输出：

- `verification/results/residuals_seven.csv` — 7 参数逐点残差（9 位小数）
- `verification/results/residuals_grid.csv` — 网格逐点残差
- `verification/results/residuals_ed50.csv` — ED50 单点
- `verification/results/summary.json` — 统计汇总

回归测试里固化了其中 31 个点的 7 参数残差（`crs/transform_d_test.mbt`），
不依赖网格文件，`moon test` 每次都会跑。网格路径的验证需要外部数据，留在脚本里。

## 9. 这一步之后，还剩什么没证明

诚实列一下：

1. **BETA2007 格网自身的绝对精度未验证。** 本库只证明"读对了、插对了"，
   0.1 m 这个数引用 BKG 的评估，不是我们测出来的。
2. **只覆盖一条多点链路。** 德国 31 点是目前唯一拿到的官方多点数据集。
   其他链路要么缺数据文件，要么缺公开点位。
3. **没有高程。** 全部是二维转换，未涉及大地水准面（OSGM15、GCG2016 等）。
4. **没有时间依赖。** 未处理板块运动与历元（ITRF↔ETRS89 的历元归算）。

这四条都写进了 `docs/DATA.md` 的"已知限制"，也写进申报书的能力边界。
